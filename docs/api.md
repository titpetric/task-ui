# API

Everything the pages do calls `/api`, JSON over the session cookie,
or over a token in an `Authorization: Bearer` header (`task-ui token
<user> <name>` prints one). Writes need the same origin. The browser
pages are the reference client; `scripts/run.sh` is the curl one.

The surface below, and the MCP tools on it, stay frozen: a change adds a
route or a tool only for a need these cannot serve, and states the reason.

| Added | For |
|-------|-----|
| `DELETE /api/artifacts` | **Delete all** on the Artifacts page: deleting the records one by one leaves the files and their history |
| `/api/runs/{id}/summary` | **Summary** on the Runs page: Claude's summary of a run, written once and kept |
| `/api/workflow-runs/{id}/summary` | **Summary** on a workflow's runs: Claude's summary of every step, written once and kept |
| `POST /api/users` | **Create user** on the Users page: the password file had no writer but `task-ui passwd` on the server |
| `/api/artifacts/files/{path}` | The preview window: a file of the tree, rendered, with its versions, and the delete of one file, which the records cannot reach |
| `/api/notes`, `list_notes`, `note_comment` | Notes, and instructions to the agent, which reads and reports on them over MCP |
| `/api/integrations`, `/api/inventory` | Settings, Integrations, which keeps the services' tokens encrypted, the inventory from Beszel, and commands run on its hosts |
| `/api/workspaces`, `workspace` on `POST /api/projects` | Workspaces: a checkout whose folder is the namespace of the projects cloned inside it, a resource the project routes cannot express. Any number of workspaces may share a repository, and deleting one takes its projects with it |
| `POST /api/workspaces/{folder}/prompt` | **Prompt** on a workspace's folder page: Claude Code on a prompt in the workspace's checkout, a run of `@claude-prompt` whose environment, `TASK_UI_PROMPT` and the workspace, `POST /api/runs` cannot carry |
| `sort` on `PUT /api/workspaces/{folder}` | **Move up** and **Move down** on the Workspaces page: the order of the workspaces in the sidebar, which no field held |
| `/api/workspaces/{folder}/keys`, `/keys/generate`, `/keys/upload`, `/keys/{name}` | **Keys** on a workspace's configure page: a workspace's own encryption key and SSH keys, and the grants that narrow an SSH key to roles and users. `/api/keys` holds the instance's keys alone, with no notion of a workspace |
| `workspace` on `PUT /api/projects/{folder}` | **Workspace** on a project's configure page: moves the project's checkout, row and the users' folder grants to another workspace. No route changed a folder's ID. `left` lists the schedules, secrets, env files and workflow steps that still name the old one |
| `workspace:<name>` scope on `/api/secrets`, `rekeyed` on `POST /api/workspaces/{folder}/keys/generate` and `/upload` | Secrets per workspace: a workspace's shared secrets, encrypted with its key and kept from every other workspace. `all` or no scope is the default workspace's, `workspace:_`; a rotation of a workspace's key writes its secrets again |
| `recursive` on `POST /api/projects` and `PUT /api/projects/{folder}`, `shallow` on a project row | **Recursive** on the clone and configure forms: off lists the project and its top-level folders alone, where discovery otherwise lists every folder of a checkout as deep as they go |
| `recursive` on `POST /api/workspaces` and `PUT /api/workspaces/{folder}`, `shallow` on a workspace row | **Recursive** on the workspace forms, the toggle projects have: off lists the workspace and its top-level folders alone; the export carries it |
| `POST /api/workspaces/{folder}/export`, `POST /api/workspaces/import` | **Export** on a workspace's configure page and **Import** on the Workspaces page: a workspace moves between instances with its keys, its grants and its secrets' ciphertext, which no route hands out. A POST keeps the passphrase out of the URL |
| `GET /api/files/{folder}/{path}` | The preview window on a folder page's **Files**: a file of the checkout, rendered as `/api/artifacts/files/{path}` renders an artifact. `/api/sources` serves only the files a pipeline reads, and no route served the rest |
| `./<path>` as `job` on `POST /api/runs` | **Run** beside a file that runs on a folder page's **Files** and in its window: the file as a job of its folder, under the folder's allow rules and hours, with the env, keys and pull of any job. A file outside the scripts folder had no job ID. `run_job`, schedules and workflow steps resolve a job the same way and take it too |
| `POST /api/keys/encrypt/rotate`, `encrypt` and `overlaps` on `GET /api/keys` | The instance row of Settings, Keys: the instance's encryption key, kept apart from the SSH keys under `TASK_UI_DATA/instance/encrypt`, has no name among them for `/api/keys/generate` to rotate. A key either encrypts or authenticates, so `overlaps` names a key held for both, and an upload of key material held for the other use, here or in any workspace, answers `409` |
| `dir` and `args` on `POST /api/runs`, `dir` and `args` on run rows, `takes_args` and `exec` on jobs | The job cards of a directory inside a folder, such as `malta/dockerfiles` in the checkout of `malta`: that directory's own targets, run there under the folder's rules, which no folder or job ID named, and arguments for an atkins job that declares `args: true`, which reach it after `--` as argv; `exec` is the command they follow, the argv of the job's `exec:` step, for the field that takes them to show what runs. Run again repeats both. Schema `run_dir_args` adds the two columns |
| `GET /api/folders/{id}/actions?dir=`, `@<skill>:<job>` as `job`, `dir` on `GET /api/runs` | The actions bar of a folder page and of a directory inside a folder: the git line of the checkout and the jobs of the atkins skills that apply in that directory. `/api/folders` lists the catalogued jobs only, and no route read `git status` or asked atkins for skills; a skill job had no job ID. A skill job runs `atkins <skill>:<job>` under the folder's rules; `run_job`, schedules and workflow steps take it too. `dir` with `job` on the runs listing keeps one directory's job apart from the folder's job of the same name. Read only, for whoever sees the folder |
| `@shell` as `job` on `POST /api/runs` | **Enter Shell** in the actions bar: an admin's interactive `bash -l` in a folder's directory, or a directory inside it, which no job of a folder runs. `403` for anyone but an admin, whatever the folder allows; no schedule or workflow step takes it |
| `POST /api/prompts` | The **Prompt** box of every folder page and every directory inside a folder: Claude Code on a prompt in that directory. `/api/workspaces/{folder}/prompt` names a workspace and no directory inside it; a prompt holds its directory alone, on either route |
| `GET /api/prompts`, `parent` on `POST /api/prompts` and `/api/workspaces/{folder}/prompt`, the note as their answer, `workspace_id` and `dir` on notes | The prompt threads under the **Prompt** box: a prompt is a question and Claude's answer, which a run cannot carry, so a prompt is a note of the folder's workspace and place, and Claude replies to it once the run ends. A reply asks again with the thread. `/api/notes` and `list_notes` list the board's notes alone, none with a workspace. Schema `note_workspace` adds the two columns |
| `PUT /api/notes/{id}`, `edited_at` on notes | Click to edit a note, a reply or a prompt: editing a note and running its answer again, which `POST` and comments cannot express. The note keeps its ID, and the agent's answer to it takes the new answer in place, from a run under the same run ID. Schema `note_edited` adds the column |
| `summarize` on `POST /api/runs` | **|>summarize** beside **Run**: a run that asks Claude to summarise it when it ends, server-side so it holds when the browser leaves. The summary is a prompt about the run, as `run` on `POST /api/prompts` asks, which no route asks on a run's end |
| `summarize` on `POST /api/inventory/run` | **Run and summarize** on the Inventory page: Claude reads every host's output as one report, after the run, in the same request |
| `GET /api/permissions`, `GET` `PUT /api/permissions/roles/{role}`, `GET` `PUT /api/permissions/users/{name}` | Permissions for roles and users: the rules of `config/permissions.yml`, a role's or a user's policy and what it allows, which no route held. `/api/users` changes the folders a user sees, not what the user may do |
| `run` on `POST /api/prompts` and `GET /api/prompts`, `about_run_id` on notes | The **Prompt** box of a run's page: a prompt about a run's output, which a folder's prompt cannot carry, the run being the context. The prompt runs in the run's folder and directory with the run's details and the end of its output, and its thread lists on the run's page, the run's history of questions and fixes, apart from the directory's prompts. Schema `note_about_run` adds the column |
| `POST` `DELETE /api/users/{id}/mcp`, `mcp` on users | **MCP access** on a user's settings page: a token made from the browser, shown once, with an expiry; tokens had no writer but the CLI. One per user, named `mcp`, lasting 30 days; a token past its expiry answers `401` "token expired, rotate it on your user settings". Tokens of `task-ui token` keep no expiry. Schema `user_auth_token_expiry` adds the column |
| `@claude-prompt` as `job` on run rows | A prompt's run belongs to the place it ran in, as `@shell` does: folder, `dir` and job `@claude-prompt`, in the recents, the runs list and the folder's run state, where `internal/claude-prompt` hid it in a folder only admins see. Runs of `internal/claude-prompt` stay as they are. `POST /api/runs` with it answers `400`: a prompt starts from `/api/prompts`, with its thread. Another user's prompt run lists in `/api/runs`, `get_run` and the `runs` topic with `prompt/view`; the asker's own always |
| `@claude` as `job` on `POST /api/runs` | **Enter Claude** in the actions bar: Claude Code in a terminal in a folder's directory, or a directory inside it, which no job of a folder runs. A shell as `@shell` is: `403` without the `shell` permission, whatever the folder allows; no schedule or workflow step takes it |
| `@claude-note` as `job` on run rows and as `TASK_UI_AGENT_JOB` | The Notes agent as a built-in job of the root, `_`, where it works, beside the other Claude jobs of every folder, so no folder `internal` lists for it: not in `/api/folders`, the sidebar or `/f/internal`, which answers `404`. `TASK_UI_AGENT_JOB` names it without a folder, as a page names `@shell`; a built-in under a folder, as `_/@claude-note` or `internal/claude-note`, stops task-ui at start. The pages and the MCP text name a run of the root by its job alone, its row keeping the folder `_`. `POST /api/runs` with it answers `400`: the board starts it on a note. Its runs list in `/api/runs`, `get_run` and the `runs` topic with `note/view`; the agent's user's own always, which it ends with `note/edit`. Runs of `internal/*` stay as they are, for admins and their starter |
| `DELETE /api/users/{id}` | **Delete** on the Users page and a user's page: the password file had no remover but editing it on the server. It removes a user who is no admin and not the caller from the file and storage at once, with their sessions, tokens and policy; `403` for an admin or yourself. It answered `405` before, and still does without a password file to write |
| `post_note`, `ask_prompt` | An agent posting and asking as its own user, by its permissions: `note_comment` answers a note and `list_notes` reads them, and no tool left a note or put a prompt to Claude in a folder |
| `prompt`, `prompt_folder` on workflows and `/api/workflows`, `enabled` on a step of `/api/workflows` and `disabled` on workflow steps, `input` on `POST /api/workflows/{id}/runs` and `run_workflow`, `workflow_run` on `GET /api/prompts`, `about_workflow_run_id` on notes | A workflow with a prompt: Claude gets the steps' output once they end, which no route asked, so a workflow summarises itself or acts on what the steps printed, or is a prompt alone. A step that stays in the chain and a run skips had no field, and a prompt takes text at run time, which the start had no body for. The prompt's thread is a note about the workflow run, listed by it and on its page, apart from its place's prompts. A workflow with no enabled step and no prompt answers `400`; a prompt takes `prompt/edit` to save and to run. Schema `workflow_prompt`, `workflow_step_enabled` and `note_about_workflow_run` add the columns |

| `GET` `POST` `PUT` `DELETE` | `/api/keys`, `/api/keys/generate`, `/api/keys/upload`, `/api/keys/{name}` | the SSH keys of `TASK_UI_SSH_DIR`, none that encrypts: `{type, name, comment, policies, users}`, `{content, name, comment, policies, users}`; `name` makes `id_<type>_<name>` for someone; `PUT` sets a key's `{policies, users}`, the roles and users whose runs get it; no secret changes with them; `GET` adds `encrypt`, the instance's encryption key, public half and fingerprint, and `overlaps`, `[{fingerprint, encrypt, access}]`, the keys held for both uses by their paths; upload answers `409` for an encryption key, private or public half (admins) |
| `POST` | `/api/keys/encrypt/rotate` | generates a new instance encryption key, keeps the old one as a backup and writes the integrations' settings again, `201 {key, rekeyed}`, `rekey_error` when that fails and the backup still opens them (admins) |
| `GET` `PUT` | `/api/env/{folder}`, `/api/env/{folder}/{path}` | the env files; `{content}` saves and generates |

## MCP

`/api/mcp` is an MCP server over the streamable HTTP transport: eleven
tools to list jobs and workflows, run them, read the runs, read, leave
and answer the notes, and ask Claude in a folder, as the token's user. Its use is in [the MCP chapter](guide/mcp.md).
